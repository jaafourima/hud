# ADR-0003: Local-first sync with an operation log

**Status:** accepted

Every device keeps a full SQLite database and works offline. Each write is an op `{record_id, entity, fields, hlc, device_id, deleted}`, applied locally and queued in an outbox. `POST /sync` pushes unsent ops and pulls server ops after a cursor.

Merge is last-writer-wins per record, ordered by hybrid logical clock (HLC); deletes are tombstones. The same merge function (`hud-sync`) runs on clients and server, and the server materializes ops into typed Postgres tables.

**Consequences:** no merge UI and no field-level CRDTs; concurrent edits to one record keep the later HLC. Property tests must show that reordered or duplicated ops converge to one state.

**Amendment (M2):** details of the implementation.
- The server keeps an append-only `ops` table (unique per user, entity, record and HLC, so replays are no-ops). A pull is `seq > cursor` for the user, minus the requesting device's own ops. One `POST /api/sync` pushes and pulls in a round trip, at most 500 ops each way; `more: true` means "ask again".
- On push, an op is applied to the plugin's Postgres table only if its HLC is newer than every op already logged for that record, so late arrivals never overwrite newer state. Deletes remove the row; the log keeps the delete, so a later older edit cannot resurrect it.
- Each user's writes are serialized with a Postgres advisory lock. That keeps one user's `seq` values committing in order, so a cursor can never skip a row that commits late.
- The server rejects ops whose timestamp is more than 24 hours ahead of its clock, since one far-future edit would otherwise win every later conflict for that record.
- The log is never compacted yet; compaction (snapshot + truncate) is a later job.
